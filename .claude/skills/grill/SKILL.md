# 설계 공격

구현을 시작하기 전에 **설계가 틀렸을 가능성을 먼저 찾는다.** 코드를 쓴 뒤에 찾으면 되돌리는 비용이 붙는다.

## 언제 도나

`dev-flow` ① 조사 다음, **② 이슈를 쓰기 전**이다.

이슈가 나온 뒤에 설계가 흔들리면 이슈를 다시 쓴다. 설계가 굳은 뒤에 이슈를 써야 「완료 조건」이 의미를 갖는다.

## 건너뛰는 경우

- 단순 버그 수정 (재현 → 고침 → 끝)
- 문서만 고치는 작업
- 이미 같은 형태로 해본 작업

**건너뛸 때는 왜 건너뛰는지 한 줄 말한다.** 조용히 생략하면 빠뜨린 건지 판단한 건지 알 수 없다.

## 방식 — 질문 라운드

한 번에 다 묻지 않는다. **3~4개씩 묻고, 답을 듣고, 거기서 파생되는 걸 다시 묻는다.**

답이 "모르겠다"면 그 자리에서 **같이 조사한다.** 모르는 채로 다음 질문으로 넘어가지 않는다.

### 묻는 축

| 축 | 질문 형태 |
| --- | --- |
| **가정** | 이게 사실이어야 설계가 성립하는데, 확인했나? |
| **대안** | 왜 A인가. B·C는 왜 아닌가. 검토는 했나? |
| **실패 모습** | 이게 틀리면 **어떻게** 드러나나. 조용히 깨지나 시끄럽게 깨지나? |
| **되돌리기** | 배포하고 나서 문제가 생기면 어떻게 돌아가나? |
| **경계** | 신뢰 경계가 어디로 움직이나. 새 입구가 생기나? |
| **규모** | 직원 10명 기준에서 이게 과한가, 모자란가? |

### 특히 파고들 것

**"그렇게 될 것이다"로 넘어간 자리.** 라이브러리가 어떻게 동작한다는 전제, 환경이 같을 거라는 전제.

```
"stopPropagation으로 막을 수 있다"       → 그 리스너가 어디 등록돼 있는지 봤나?
"로컬에서 되니까 운영에서도 될 것이다"   → 환경이 뭐가 다른가?
"검증이 걸릴 것이다"                     → 그 값이 검증까지 도달하는 경로를 따라갔나?
```

## 끝낼 때

설계가 바뀌었으면 **무엇이 왜 바뀌었는지** 정리한다. 그게 이슈의 「판단 근거」가 되고 나중에 PR 본문으로 간다.

바뀐 게 없으면 **"공격했는데 안 바뀌었다"고 말한다.** 그것도 결과다.

## 하지 않을 것

**질문을 위한 질문을 만들지 않는다.** 답이 설계를 바꾸지 않을 질문은 빼고, 왜 뺐는지도 말하지 않는다 — 그냥 안 묻는다.

**비판을 위해 비판하지 않는다.** 괜찮은 설계면 괜찮다고 말한다.
