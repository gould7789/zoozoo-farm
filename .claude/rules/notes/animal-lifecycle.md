# 동물의 생애 — 들어오고 나가는 것

## 한 칸으로는 안 됐다

도입 초기에는 `active = false` 하나로 삭제를 표현했다. **세 가지 다른 사건이 거기 겹쳤다.**

| 사건 | 남아야 하는 것 |
| --- | --- |
| 폐사 | 사망일, 사인 — **폐사보고서를 쓴다** |
| 분양 | 분양일, 분양처 — 흔하지 않지만 실제로 있다 |
| 입력 실수 | 아무것도. 진짜 지워야 한다 |

한 칸에 담으면 **나중에 구분할 수 없다.** 사망일이 없으면 보고서는 종이와 카카오톡으로 돌아가는데, 이 앱을 도입한 이유가 그 흩어짐이었다.

## 테이블이 아니라 컬럼인 이유

**입수가 이미 컬럼이다.**

```ruby
t.date "acquired_at"        # 입수일
t.text "acquisition_note"   # 입수 경위
t.integer "exit_reason"     # 폐사 0 / 분양 1
t.date "exited_on"
t.text "exit_note"          # 사인 또는 분양처
```

퇴출을 별도 테이블로 빼면 **들어온 건 컬럼, 나간 건 테이블**이 되어 같은 성질의 사실을 찾는 곳이 둘로 갈린다.

둘째로 `animals` 에는 `created_by_id` 가 **없다.** 다른 기록 테이블에는 전부 있다. `animals` 는 기록이 아니라 **대장(master)** 이고, 작성자를 안 남기는 쪽이 일관된다.

### `exit_note` 한 칸이 사인과 분양처를 겸한다

`active` 의 문제는 한 칸이 둘을 담는 것이 **아니라 구분자가 없다**는 것이었다. 여기는 `exit_reason` 이 구분자라 어떻게 읽을지가 정해진다. `acquisition_note` 가 이미 같은 일을 한다.

## CHECK 가 못을 박는다

```sql
CHECK ((active = false) = (exit_reason IS NOT NULL))
CHECK ((exit_reason IS NULL) = (exited_on IS NULL))
```

첫 번째가 **「나갔는데 목록에 보이는 행」과 「사라졌는데 이유를 모르는 행」을 둘 다 불가능하게** 만든다. `active` 를 파생값으로 지우지 않고 남긴 이유는 목록 필터가 쓰는 빠른 칸이기 때문이고, 그래서 둘이 어긋나지 않게 묶어야 했다.

두 번째 — **날짜는 필수다.** 사인은 몰라도(갑자기 죽는 경우) 날짜는 모를 수 없다. 모르면 발견일을 적는다. 날짜 없는 폐사 기록은 보고서에 못 쓴다.

> **모델에도 같은 검증을 둔다.** DB 에만 두면 폼에서 사유를 비웠을 때 검증 에러가 아니라 **500** 으로 드러난다.

`active` 와 `exit_*` 는 **한 번에 쓴다.** 따로 업데이트하면 중간 상태가 제약에 걸린다.

## 입력 실수는 물리 삭제한다 — 규칙이 아니라 숫자로 막는다

처음에는 `admin/users` 의 패턴(기록이 있으면 못 지운다)을 가져오려 했다. **막다른 길이 있다.**

```
잘못 등록 → 모르고 기록 1건 추가 → 실수를 알아차림 → 영영 못 지움
```

그래서 조건을 걸지 않고 **기록 건수를 보여주고 종명을 입력하게 한다.** 입력 실수한 개체는 기록이 0~2건, 실재한 개체는 수십 건이라 숫자가 눈에 들어오면 사람이 멈춘다.

**종명 확인은 서버에서 한다.** 브라우저에서만 막으면 되돌릴 수 없는 조작이 폼을 거치지 않은 요청에 그대로 열린다.

그 덕에 `dependent: :destroy` 를 **안 바꿔도 됐다.**

### 사진은 동기로 지운다

`has_one_attached` 의 기본 `dependent` 는 **`purge_later`** 다. 잡 워커가 없어(`:async`) 무료 플랜 인스턴스가 잠들면 **잡이 사라지고 스토리지에 파일이 남는다.** `notes/animal-photo.md` 의 함정이 그대로 되살아나는 자리다.

## 내보낸 개체에는 기록을 **추가**할 수 없다

막지 않으면 사망일 이후의 급여 기록이 **에러 없이 저장된다.** 조용히 깨지는 종류라 폐사보고서를 쓸 때야 드러난다.

`AnimalScoped` 에 `only: [:new, :create]` 로 건다. **`edit` · `update` · `destroy` 는 막지 않는다** — 지난 기록의 오타를 고치는 것은 정당하고, 해로운 것은 새 기록이 생기는 쪽이다.

화면에서도 추가 버튼을 숨긴다. 서버가 막아도 **누를 수 있는 버튼을 두면 막혔다는 사실을 눌러봐야 안다.**

## 군집의 부분 폐사는 지원하지 않는다

`individual_count > 1` 인 행은 **이름 없는 종**(토끼·기니피그)뿐이다. 폼의 도움말이 그 설계를 말한다 — 「개별 이름이 없는 동물 종의 경우 총 마리 수를 입력해주세요」.

| 상황 | 어떻게 |
| --- | --- |
| 이름 있는 개체가 폐사 | 그 행을 내보낸다. 보고서를 쓴다 |
| 토끼 48마리 중 3마리 폐사 | `individual_count` 를 45로 수정한다. **폐사 기록은 남지 않는다** |
| 토끼가 전멸 | 행을 통째로 내보낸다 |

두 번째 줄이 제약이다. **그 종은 폐사보고서를 쓰지 않으므로** 받아들였다.

> 행을 자동으로 쪼개 「48마리 중 1마리」를 표현하는 안을 설계했다가 버렸다. 이름 없는 군집은 **개체 동일성이 없어서** 쪼개도 되돌려도 무엇이 무엇인지 말할 수 없다.

내보내기 모달은 `individual_count > 1` 일 때 **전체 마리 수를 경고**한다.

## 보관 화면은 하나다

`/archive` 하나이고 **사진 카드로 만든다.** 그게 곧 갤러리다. 목록과 갤러리를 나누면 같은 데이터를 두 화면이 보여주고, 한쪽을 고칠 때 다른 쪽을 빠뜨린다.

입구는 **홈의 관 카드 바로 아래 링크 한 줄**이다.

| 두지 않은 곳 | 왜 |
| --- | --- |
| 홈의 「주요 현황」 | 그 영역은 **현재형**이다. 폐사는 현황이 아니라 이력이라 축이 섞인다 |
| 하단 탭·사이드바 | Admin 기준 탭이 이미 4개다. **1년에 몇 번 쓰는 기능이 매일 쓰는 것의 자리를 뺏는다** |

**숫자를 붙이지 않는다.** 「(12)」는 줄지 않고 쌓이기만 해서 5년 뒤 「(312)」가 된다. 판단에 쓸 수 없는 수를 위해 홈이 열릴 때마다 COUNT 를 한 번 더 돈다.

조회는 **Staff·Admin 공통**이다. 동물 상세가 이미 공통이고 「그 아이 언제 죽었지」는 둘 다 묻는다. 내보내기·되돌리기·완전 삭제만 Admin 이다.

관을 가로지르므로 `AnimalsController`(zone 하위)에 둘 수 없어 **컨트롤러가 하나 더 있다.**

## 되돌릴 수 없는 조작은 라우트부터 나눈다

| 조작 | 라우트 |
| --- | --- |
| 내보내기 | `DELETE /zones/:id/animals/:id` |
| 되돌리기 | `POST .../restore` |
| 완전 삭제 | `DELETE .../purge` |

`destroy` 에 플래그로 섞으면 **파라미터 하나 차이로 복구 불가능한 일**이 일어난다.
