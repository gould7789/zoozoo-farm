## 3. 반드시 알고 시작해야 할 지뢰 3개

이 프로젝트는 이미 Active Storage 관련 문제를 한 번 겪었고, **당시의 우회 설정이 그대로 남아 있습니다.**

### 🔴 지뢰 1 — `variant_processor = :disabled`가 살아 있음

`config/application.rb:15`

```ruby
config.active_storage.variant_processor = :disabled
```

과거 PR #66에서 부팅 오류를 우회하려고 넣은 줄입니다. 이 상태에서는:

- `photo.variant(resize_to_limit: [...])`를 써도 **에러 없이 리사이즈가 무시됩니다.** 조용히 실패합니다.
- 추가로, Rails 이슈 **#58313**에 따르면 `:disabled`로 두면 **이미지 분석기까지 함께 꺼져서 `width`/`height` 메타데이터가 기록되지 않습니다.** (Rails 8.0 → 8.1.3.1 리그레션. 수정 PR #58314는 아직 리뷰 중)

### 🔴 지뢰 2 — `ruby-vips`가 Gemfile에 없음

Gemfile 48행에 `gem "image_processing", "~> 2.0"`은 있지만 `ruby-vips`가 없습니다.
`image_processing` 2.0이 `ruby-vips`를 런타임 의존성에서 제거했기 때문입니다.

**지뢰 1을 해결하려고 `:disabled`를 지우는 순간 부팅이 실패합니다.** 배경은 다음과 같습니다.

1. Rails 8.1.3.1의 보안 패치가 `activestorage/lib/active_storage/transformers/vips.rb` 상단에 `require "image_processing/vips"`를 추가
2. `ruby-vips`가 없으므로 LoadError 발생. 메시지는 `ImageProcessing::Vips requires the ruby-vips gem. ...`
3. `engine.rb`의 `rescue LoadError`가 `when /libvips/` / `when /image_processing/`(소문자)로만 매칭 → 어디에도 안 걸림 → `raise`
4. 결과적으로 `bin/rails` 명령 자체가 전부 죽음

> 이건 Rails 측 버그였고, `8-1-stable` 브랜치에 2026-08-10 수정이 머지되었습니다(PR #58414). `main` 대상 PR #58417은 아직 열려 있습니다.
> **해결책은 단순합니다. `ruby-vips`를 Gemfile에 추가하면 됩니다.**

### 🔴 지뢰 3 — 프로덕션 스토리지가 로컬 디스크 (가장 큼)

`config/environments/production.rb:25`

```ruby
config.active_storage.service = :local
```

`config/storage.yml`의 `local`은 Disk 서비스이고 저장 경로는 `Rails.root.join("storage")`입니다.
그런데 `render.yaml`은 `plan: free`이고 **퍼시스턴트 디스크 설정이 없습니다.**

→ **재배포하거나 인스턴스가 재시작되면 업로드된 이미지가 전부 소멸합니다.**
→ 이번 작업에서 반드시 외부 오브젝트 스토리지로 전환해야 합니다.

- [ ] Gemfile에 `gem "aws-sdk-s3", require: false` 추가

- [ ] `config/storage.yml`에 서비스 추가

```yaml
supabase:
  service: S3
  access_key_id: <%= ENV["SUPABASE_S3_ACCESS_KEY_ID"] %>
  secret_access_key: <%= ENV["SUPABASE_S3_SECRET_ACCESS_KEY"] %>
  region: <프로젝트 리전>
  bucket: <버킷명>
  endpoint: https://<프로젝트ref>.supabase.co/storage/v1/s3
  force_path_style: true
```

> `endpoint`와 `force_path_style: true`가 빠지면 원인을 알기 어려운 403이 발생합니다.

- [ ] `production.rb`의 `config.active_storage.service`를 `:supabase`로 변경
- [ ] `render.yaml`의 `envVars`에 위 키들을 `sync: false`로 추가

## 5. 제약 조건 (설계 시 반영)

- **Render free plan: 메모리 512MB.** 큰 원본 이미지를 리사이즈하면 OOM 위험.

  > **2026-08-25 정정.** 이 항목은 원래 *"variant는 백그라운드로 처리할 것"* 이었으나 **틀린 대책이다.**
  > Render 무료 플랜은 서비스가 하나뿐이라 worker를 띄울 수 없고, 잡은 `SOLID_QUEUE_IN_PUMA`로
  > **Puma와 같은 프로세스에서** 돈다. 리사이즈가 같은 512MB 안에서 일어나므로 OOM 위험이 그대로다.
  > 게다가 무료 플랜은 유휴 시 서버가 내려가 워커도 멈추므로 "미리 만들어둔다"가 보장되지 않는다.
  >
  > **대책은 병목을 서버가 아니라 클라이언트로 옮기는 것이다.**
  > 1. **브라우저에서 전송 전 리사이즈** (Stimulus + canvas, 예: 긴 변 1600px).
  >    전송량·서버 메모리·저장 용량이 동시에 줄고 업로드 자체가 빨라진다
  > 2. **서버 측 크기 상한은 안전망으로만** (15~20MB 권장). 폰 사진은 3~8MB라 사실상 전부 통과한다.
  >    사용자에게 축소를 강요하는 장치가 아니다. JS가 실패했을 때를 위한 마지막 방어선이다
  > 3. variant는 첫 조회 시 생성 후 저장돼 재사용된다. 원본이 1600px이면 생성이 가벼워
  >    동시 요청이 겹쳐도 위험하지 않다
  >
  > **미확인**: 아이폰 기본 포맷 HEIC를 브라우저 canvas가 읽을 수 있는지. iOS가 업로드 시
  > JPEG로 변환하는 동작이 있으나 실기 확인이 필요하다. 못 읽으면 그 경우만 서버로 원본이 간다.
- **Supabase free plan:** 파일 스토리지 1GB, 스토리지 egress 5GB, 파일당 최대 50MB. 무료 플랜에는 Supabase 자체의 온더플라이 이미지 변환 기능이 없으므로, 리사이즈는 앱에서 vips로 처리합니다.
- **Supabase free는 DB 활동이 7일간 없으면 프로젝트가 일시정지됩니다.** 정지되면 DB·인증·**스토리지가 동시에** 멈춥니다. 현재 UptimeRobot으로 핑을 보내고 있으나, **그 엔드포인트가 실제로 DB 쿼리를 발생시키는지는 미확인 상태**입니다. 이번 작업 중에 확인하고, 필요하면 가벼운 SELECT를 수행하는 헬스체크 엔드포인트를 추가하세요.
- 시크릿은 절대 코드에 하드코딩하지 말 것. ENV 또는 Rails credentials 사용.

## 8. 상류 버그 감지 프로토콜 (작업 내내 적용)

작업 도중 "라이브러리 태생적 결함"으로 보이는 것을 만나면, 그 자리에서 처리하지 말고 아래 절차를 따르세요.

### 8-1. 의심 트리거

다음 중 하나라도 해당되면 **상류 버그 후보**로 간주합니다.

- 공식 문서대로 했는데 문서와 다르게 동작한다
- 에러 메시지가 **실제 원인과 다른 것**을 가리킨다 (원인을 찾는 데 문서가 도움이 안 됐다)
- 라이브러리 **소스 코드를 직접 열어봐야** 원인을 알 수 있었다
- 버전을 올린 직후부터만 발생한다 (리그레션 의심)
- 라이브러리 코드의 **주석이나 문서가 서술하는 의도와 실제 동작이 다르다**
  - ※ 지난번 케이스가 정확히 이것이었습니다. Rails 측 주석은 "엔진이 이를 실행 가능한 경고로 보고한다"고 적혀 있었는데 실제로는 예외가 그대로 올라왔습니다.

### 8-2. 🚨 가장 강력한 신호 — 우회 코드를 작성하려는 순간

다음 중 하나를 하려는 순간, **손을 멈추고 8-3으로 가세요.**

- 설정으로 기능을 끄기 (`= :disabled`, `= false`)
- monkey patch 작성
- 원래 없어도 될 `rescue` 추가
- 버전 고정 / 다운그레이드
- "일단 이렇게 하면 되니까" 하고 넘어가기

**우회 코드는 상류 버그의 가장 확실한 지표입니다.** 우회가 필요하다는 건 라이브러리가 의도대로 동작하지 않는다는 뜻이기 때문입니다.

### 8-3. 즉시 할 일 (5분, 미루지 말 것)

1. 해당 리포지토리 이슈를 **에러 메시지의 특징적인 단어**로 검색 (닫힌 것 포함)
2. 없으면 PR 목록도 검색 — 이미 고쳐졌는데 릴리스 전일 수 있음
3. 결과를 8-4의 로그에 기록

> **이 단계를 나중으로 미루면 안 됩니다.** 지난번에 이틀 늦어서 기회를 놓쳤습니다. 인기 있는 프레임워크의 리그레션은 며칠 안에 다른 사람이 가져갑니다.

### 8-4. 기록 방법

`docs/oss-candidates.md`에 아래 형식으로 계속 append 하세요. 우회 코드를 커밋하는 PR 본문에도 같은 내용을 요약해 남깁니다.

```markdown
## [날짜] 라이브러리명 버전 — 한 줄 요약

- **증상**:
- **재현 절차**:
- **원인 추정**: (파일 경로:행 번호, 해당 코드)
- **상류 이슈 검색 결과**: (없음 / #번호 — 상태)
- **적용한 우회**: (커밋 해시)
- **판정**: 내 설정 실수 / 상류 버그 후보 / 상류에서 이미 처리됨
- **다음 액션**:
```

### 8-5. "내 실수"와 "상류 버그" 구분하기

상류에 이슈를 올리기 전에 반드시 확인합니다.

- [ ] **최소 재현** — `rails new`로 만든 빈 앱에서도 재현되는가? 재현되면 상류 버그일 가능성이 높습니다.
- [ ] **소스 확인** — 라이브러리 코드의 어느 줄에서 갈라지는지 짚을 수 있는가?
- [ ] **버전 비교** — 이전 버전에서는 정상 동작하는가? 리그레션이면 근거가 훨씬 강해집니다.

세 개가 다 되면 그대로 이슈 본문이 됩니다.

### 8-6. 작업자(에이전트)에게 주는 지시

- 우회 코드를 제안할 때는 **반드시 "이것은 우회입니다"라고 명시**하고, 8-3의 검색 결과를 먼저 보고할 것
- 조용히 `rescue`를 추가하거나 설정을 끄고 넘어가지 말 것. **이것이 지난번 기회를 놓친 직접적인 원인입니다.**
- 라이브러리 내부 코드를 읽어서 원인을 파악한 경우, **파일 경로와 행 번호를 반드시 사용자에게 보여줄 것**
- 8-4의 로그 작성은 사용자와 함께 할 것. 사용자가 나중에 그 내용을 직접 설명할 수 있어야 합니다.
